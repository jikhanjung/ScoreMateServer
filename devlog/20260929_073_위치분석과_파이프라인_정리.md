## 출발점 — 두 질문
1. "MusicXML 만 가지고도 마디/보표/시스템 위치를 알 수 있어?"
   - MusicXML 은 마디 순서 · 번호 · 박자는 담는다. **PDF 위의 좌표는 담지 못한다**
   - 레이아웃 요소(`<print>` · `<system-layout>` · `default-x`)가 있어도 그 프로그램의 조판 기준이라 실제 PDF 와 어긋난다
   - 그래서 **줄 · 쪽 바뀜만** MusicXML 에 넣었다(0.10.3)
2. "모델한테 system 의 bbox 를 출력해 달라고 할 수도 있을 것 같은데?"
   - 해 봤더니 기대보다 훨씬 정확했다(070) → 모든 악보에 붙였다(071) → 세 레인을 파이프라인 하나로 묶었다(072)

## 지금의 처리 흐름
```
PDF 올리기 ─ 요청 안: 쪽수 · sha256 · 표지
   │
   └ cron 5분 score_pipeline.sh (잠금 하나, 할 일이 없어질 때까지)
       ① PDF 분석     컨테이너 · 수 초       TV 앱 Kotlin 분석 그대로(066 · 068). 벡터 PDF 의 정답
       ② 모델 위치    Codex · 쪽당 20~40초   벡터: ①의 검산(쪽마다 구조 · pt 오차) / 스캔: 기기 layout
       ③ 악보 인식    Codex · 쪽당 2~4분     믿을 수 있는 위치(① 또는 ②)의 보표 수 · 시스템 수로 검산,
                                              줄 · 쪽 바뀜 확정, 인식 마디 수 = 위치 마디 수?
       우선순위: ① 전부 → ② 한 쪽 → ③ 한 쪽 → 다시(짧은 악보부터) — 새 악보가 긴 인식의 쪽 사이에 끼어든다
   │
   └ 저장될 때마다 서로 맞춘다
       - ①이 새로 저장되면 → ②의 검산을 다시 계산
       - ③이 저장되거나 파트 이름을 고치면 → ① · ② 파일의 보표 이름
       - 파일이 바뀌면 sha256 이 새로워지고, 기기는 다음 동기화에 다시 받는다
```

## 두 위치 분석 비교 (운영 네 곡, 80쪽)
| 악보 | 시스템 · 마디 | ②와 ①의 구조가 같은 쪽 | 평균 · 최대 오차 |

| Arpeggione | 82 · 278 | 28/28 | 0.28 · 1.8pt |
| Moldau | 84 · 268 | 42/42 | 0.26 · 0.8pt |

- **항목은 같다**: 시스템 테두리 · 보표 · 마디선 · 보표 이름 · 박자표. 마디 상자도 같은 규칙이다
  - 파일 모양도 같다(앱 `ScoreLayout` + `measures` · `staves`)
- 다른 점
  - 보표 이름은 **모델이 더 잘 읽는다**: 글자가 아닌 이름도, MuseScore 의 글자별 이름도 읽는다
  - 다만 한글 비슷한 글자는 틀린다(예완 → 예원). 그래서 기기용 이름은 **사람이 고친 파트 이름**을 쓴다(0.12.2)
  - 박자표는 모델이 보표마다 적었다 → 시스템당 하나로 모았다(0.12.1)
  - 좌표 정밀도: ① 은 PDF 원래 값, ② 는 0..1000 눈금
- 인식(③)의 마디 수도 네 곡 모두 위치 분석과 같다(069)
  - 즉 **서로 독립인 세 방법**(벡터 규칙 · 모델 위치 · 모델 전사)의 마디 수가 모두 같다

## 기기(TV 앱)가 받는 것
- PDF · MusicXML · layout 을 동기화 한 번에 받는다
  - `layout.source`: `pdf` 또는 `model`
  - 그 밖: `analyzer_version` · `pdf_sha256`
  - 보표 이름은 파트 이름(`labels_from: musicxml-parts`)
- 앱 저장소 P06 에 알렸다: §11 musicxml · §12 layout · §13 `source` · §14 보표 이름. 앱 변경이 필요한 것은 없다

## 배운 것
- **모델의 위치 읽기는 문자 인식보다 훨씬 정확하다**
  - 좌표는 눈금 한 칸 안이었다
  - 이름 · 음높이 같은 "무엇" 은 조용히 틀린다(예원 · 조표)
  - → 위치는 모델에 맡기고, 이름은 사람이 확인한다
- 세 방법의 결과가 서로 맞으면 믿을 수 있다. 어긋난 곳(쪽)만 사람이 보거나 힌트에서 뺀다
- 순서가 있는 여러 단계는 레인을 따로 두기보다 **한 곳에서 쪽 단위로 조율**하는 편이 단순하고 공정했다
