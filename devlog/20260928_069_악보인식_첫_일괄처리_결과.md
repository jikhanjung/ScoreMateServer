## 속도 — 무엇이 호출 시간을 정하나
| 단계 | K488 1쪽 기준 | 비고 |
|---|---|---|
| MusicXML · high · 2쪽씩(처음) | 쪽당 약 1,310초 | 2쪽 호출 35~45분. 첫 악보(SM-000234705)는 3~4쪽에서 40분 시간 초과 |
| MusicXML · medium | 1,039초 | 34마디 중 33 같음 — 21% 빠를 뿐 |
| 짧은 형식 · medium | 198초 | **조표를 샵 3 으로 잘못 읽음**(G 가 모두 G#) |
| **짧은 형식 · high (채택)** | **273초** | 34마디 중 33 같음(나머지 1 도 같은 음을 두 성부로 적은 것) |

- 호출 시간은 추론이 아니라 **쓰는 양**이 정했다
  - MusicXML 은 음표 하나에 약 350바이트 · 쪽당 출력 약 4만 토큰이었다(추론은 3천)
  - 짧은 형식은 약 9천 토큰이다
- 2쪽 호출은 느리고 깨지기 쉬웠다(긴 XML 을 JSON 문자열로 쓰다 태그를 잘못 닫음) → **1쪽씩** + 실패하면 쪽을 나눈다
- 최종 처리량: 70쪽이 약 3시간 반 → **보통 악보는 올린 뒤 한 시간 안쪽**

## 조용히 틀리는 곳과 막은 장치
박 길이 검산만으로는 안 잡히는 것들 — 모두 한 번씩 실제로 겪었다.

| 틀림 | 사례 | 막은 장치 |
|---|---|---|
| 조표를 잘못 셈 → 그 음이 전부 틀림 | 짧은 형식 · medium 의 K488(샵 2 → 3) | 첫 쪽 곡 정보 호출이 조표를 따로 읽는다. 다르면 "다시 세라"(0.9.7). effort high |
| 한글 파트 이름의 비슷한 글자 | K488 예완 → 예원 | 웹에서 파트 이름 고치기(0.9.8 · 0.9.9). 파일 · sha256 이 바뀌어 기기가 다시 받는다 |
| **제목에서 악기를 지어냄** | Arpeggione 기타 셋 → "Arpeggione + Pianoforte(보표 2)" | 보표 분석을 먼저 하고 "시스템마다 보표 N개"를 알려 준다. 파트 보표 합 ≠ N 이면 되돌린다. 이름은 인쇄된 것만(없으면 Staff n), 제목에서 짐작 금지(0.10.2) |
| XML 형식 깨짐 | 로컬 Moldau 3~4쪽 | 검산 → 오류를 붙여 한 번 더 → 그래도 안 되면 쪽을 나눈다 |
| 파트를 한 부 복사 | (의심했으나 아니었다) | 파트끼리 같은 마디 수 · 음 대조로 확인했다 |

남은 약점: **음높이** 자체는 자동으로 못 잡는다. 사람이 들어보기(0.9.9)나 MuseScore 로 확인한다.
